やったこと（変更したファイル・設定・処理、または設計した取得方法）：
変更箇所を1つずつ変えた4条件を、変更前と比較した（各条件で変更は1か所のみ。実行後は毎回元に戻した）。
- TOP_K=2：app/config.py の RAG_TOP_K を 5 → 2
- TOP_K=8：app/config.py の RAG_TOP_K を 5 → 8
- 指示文1行削除：app/agent.py の INSTRUCTIONS から「複数の話題や回を組み合わせる質問では、必要に応じて検索を分けて根拠を集める。」を削除
- ツール説明補足：app/tools.py の search_materials の docstring にある「queryに調べたい内容を指定する。」を、次の4行に置き換え
  - queryには質問文をそのまま入れず、調べたい話題のキーワードを2〜4語で指定する。
  - 結果は質問との距離が近い順に上位数件のページ。距離が近くても答えを含むとは限らない。
  - 質問に複数の話題が含まれる場合は、話題ごとに分けて呼び出す。
  - 結果に答えが見つからない場合は、別の言い換えで再検索する。
  （uv run python -m app.agent --list-tools で、モデルに見える説明が変わったことを確認）

比較した質問と、固定した条件（モデル・対象資料など）：
- 質問：「コンパクションとセッションをまたぐメモリの違いは？日々のメモは全部長期メモリになる？」
- 期待する根拠：第3回 p.13, 39, 40（演習資料 p.20 の「複数ページ」の質問）
- 固定した条件：モデル gemini-3.5-flash-lite、対象資料は第1〜3回の本講義、質問文、変更箇所以外のコード
- 実行方法：既定モード（ベクトル検索）を --trace 付きで実行。最初に各条件1回ずつ実行したところ、同じ設定でも検索回数が1回と2回に分かれたため、スクリプトで各条件3回ずつ実行し直した。実行順は条件を順番に回し、API の混雑の影響が特定の条件に偏らないようにした。503 エラーの回は待機して再実行した。

改善した例と、残る失敗・制約：
- 改善した例：指示文1行削除では、根拠の取得を保ったまま入力トークンが57%、推定費用が37%減った。この質問では、1回の検索で必要なページがそろった。
- 残る失敗：TOP_K=2 では p.13 が3回とも取得されなかった。ツール説明補足では、「話題ごとに分けて呼び出す」と書いたのに検索をまとめる実行が多く、p.13 の取得も減った。
- TOP_K=8 は、根拠は変更前と同じで、費用と時間だけが増えた。
- 制約：
  - 質問は1問、各条件3回のみ。検索回数の傾向は見えたが、統計的に確かめたわけではない。
  - 時間は同じ条件でも約3倍ばらつき、503 エラーも多発したため、時間の比較は参考値にとどまる。
  - 回答の正誤は、引用ページと、2つの問いの要点を示す語（「要約」「基準を超え」）が全15回の回答に含まれることで確認した。キーワードによる簡易確認であり、本文を詳しく採点したわけではない。

気づき・疑問：
- 最初に各条件1回ずつ実行した時点では、変更前の2回目がたまたま1回検索だったため、指示文の削除に効果がないように見えた。3回ずつ実行して初めて差が見えた。講義の「実践知も、測って決める」は、1回の実行では測ったことにならないと実感した。
- 指示文の1行は、検索の分け方を実際に変えていた。一方、ツール説明に書いた「分けて呼び出す」は効かず、逆の行動が出た。同じ内容でも、どこに書くか、他の文と組み合わさるかで効果が変わると考えられる。講義で紹介された「説明文の補足で悪化する場合もある」という結果と一致する。
- 取得件数は多いほど良いわけではなく、TOP_K=8 では費用だけが増えた。必要なページが上位に入る質問では、件数より検索語の作り方の方が結果を左右していた。
- 疑問：ツール説明補足で検索をまとめるようになった原因は、「キーワードを2〜4語で」の一文なのか。4行を1行ずつ分けて試せば切り分けられるか。
